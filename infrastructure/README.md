# Infrastructure

Database engines, session factory, Alembic migrations and the shared repository helpers for
the CDTM Community platform.

This folder is deliberately small. Domain ORM models live in the bounded contexts under
`backend/`; `infrastructure/` owns only what all of them share: the declarative base, the
engines, the metadata aggregation Alembic reads, and the error mapping every repository wraps
its calls in.

Run every command below from the repository root. Alembic's `env.py` imports
`backend.core.settings` and `infrastructure.models`, so it needs the root on `sys.path`
(`PYTHONPATH=.`, which the `poe` tasks set for you).

## Directory map

```text
infrastructure/
  db.py
    Base                  # DeclarativeBase with the constraint naming convention
    get_async_engine()    # asyncpg engine for the app; pooler-aware, statement timeout
    get_session_factory()  # async_sessionmaker, expire_on_commit=False
    get_db()              # FastAPI dependency: one AsyncSession per request
    get_sync_engine()     # psycopg engine for Alembic and scripts
    reset_engines()       # forget cached engines (tests, after changing settings)
  models.py               # imports every context's orm_models so Base.metadata is complete
  repository.py
    run_db(op, fn)        # driver errors -> backend.core.exceptions
    utc_now()             # the only clock
  alembic.ini             # config; sqlalchemy.url is resolved at runtime from settings
  alembic/
    env.py                # reads DatabaseSettings.migrator_url
    script.py.mako        # revision template
    versions/             # ordered revisions
```

Settings live in `backend/core/settings/`, loaded from the repository-root `.env` (template:
`.env.example`).

## Two engines, one URL

`DATABASE_URL` is the single connection string. `DatabaseSettings` derives both drivers from
it and normalises whatever prefix you pasted (`postgres://`, `postgresql://`,
`postgresql+psycopg2://` all work):

| Property | Driver | Used by |
| --- | --- | --- |
| `async_url` | `postgresql+asyncpg://` | FastAPI, repositories, loader scripts |
| `sync_url` | `postgresql+psycopg://` | one-off scripts |
| `migrator_url` | `postgresql+psycopg://` | Alembic, from `DATABASE_MIGRATOR_URL` if set |

`DATABASE_MIGRATOR_URL` exists so migrations can use a direct connection while the app runs
through a pooler. It defaults to `DATABASE_URL`.

## Local database

Any local Postgres 13 or newer works. There is no Docker Compose file in this repository.

```bash
createdb cdtm_community
createdb cdtm_community_test          # the integration suite truncates this one
```

```bash
# backend/core/.env
DATABASE_URL=postgresql://localhost:5432/cdtm_community
```

Then apply the schema and, if you want something to look at, seed it:

```bash
uv run poe migrate
uv run poe seed
```

`pg_trgm` is created by the first migration. On a local Postgres that needs a superuser (or a
trusted extension) the first time; if `CREATE EXTENSION` is refused, run it once by hand as
`postgres`.

## Supabase

Supabase provides Postgres, Auth and Storage. Migrations still go through Alembic, never
through the Supabase CLI (ADR 0003): Alembic owns the schema and
`tests/integration/test_migrations.py` proves it.

Two connection strings, and the distinction is not cosmetic:

| | Direct | Transaction pooler |
| --- | --- | --- |
| Port | 5432 | 6543 |
| Prepared statements | yes | **no** (PgBouncer, transaction mode) |
| Use for | Alembic, and a single long-lived API process | serverless or many short-lived replicas |

`get_async_engine` detects a pooler URL (`:6543/` or `pooler.supabase.com`) and disables
asyncpg's statement cache for it. Without that you get intermittent
`prepared statement "__asyncpg_stmt_N__" already exists` under load.

```bash
# backend/core/.env, Supabase profile
DATABASE_URL=postgresql://postgres.<ref>:<password>@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
DATABASE_MIGRATOR_URL=postgresql://postgres:<password>@db.<ref>.supabase.co:5432/postgres
```

Full detail, including the statement timeout and the pool settings, is in
[`../docs/database-design.md`](../docs/database-design.md) section 11.

## Migration commands

```bash
uv run poe migrate                                                       # upgrade head
PYTHONPATH=. alembic -c infrastructure/alembic.ini current               # current revision
PYTHONPATH=. alembic -c infrastructure/alembic.ini heads --verbose
PYTHONPATH=. alembic -c infrastructure/alembic.ini history --verbose
PYTHONPATH=. alembic -c infrastructure/alembic.ini revision -m "describe change"
PYTHONPATH=. alembic -c infrastructure/alembic.ini revision --autogenerate -m "describe change"
PYTHONPATH=. alembic -c infrastructure/alembic.ini downgrade -1          # disposable databases only
```

Always read an autogenerated revision before committing it. Check `ondelete` behaviour on
new foreign keys, `CHECK` constraint text, partial index predicates, array server defaults,
and that the downgrade actually reverses the upgrade.

`env.py` sets `compare_type=True` and `compare_server_default=True`, so autogenerate does
notice a changed type or default. It does not notice a renamed column: that arrives as a drop
plus an add, and turning it into a rename is a manual edit.

## Migration history

| Revision | Scope | Contents |
| --- | --- | --- |
| `001_initial_schema` | whole platform | All 21 tables of the merged platform: members (roster, scrape, entries, intents, classes, CA details, positions, educations), network (`saved_members`, `intro_requests`), paths (`member_paths`), events, announcements, housing, identity (`accounts`), job board (`companies`, `jobs`, `seekers`), core (`ask_quota`), plus every CHECK constraint, partial index and the `pg_trgm` extension |

There is one revision because the merge was a rebuild, not an evolution. The two predecessor
apps had their own histories (`jobboard/infrastructure/supabase/supabase/migrations/` applied
with `supabase db push`, and nothing at all for the static community tool) and neither had a
production database worth preserving. Starting from one reviewed baseline was cheaper than
reconciling them.

`001_initial_schema` is hand-frozen from an autogenerate run: one `_create_<table>` builder
per table, an explicit `UPGRADE_ORDER` in foreign-key order and a `DROP_ORDER` that reverses
it, so the file reads like the data model. The `pg_trgm` extension is created on upgrade and
deliberately not dropped on downgrade, since other schemas in the same database may depend on
it.

It is still the only revision after the context split of ADR 0007. The split moved ORM classes
between packages and changed no table: foreign keys were already string references
(`"members.id"`), and `infrastructure/models.py` imports all nine model modules, so
`Base.metadata` came out identical. Three later additions (`housing_listings.furnished`,
`housing_listings.view_count` and the `ask_quota` table) were folded into the baseline rather
than chained after it, because no production database exists yet to migrate. A development
database that predates them is caught up by hand with `alter table` and then still reports
`001_initial_schema (head)`; `alembic check` is the proof that the baseline and the ORM agree.

The downgrade is intended for disposable databases only.

## Adding a table

1. Add the ORM model to `backend/<context>/infrastructure/orm_models.py`.
2. Make sure the context is imported in `infrastructure/models.py`. A new bounded context that
   is not imported there is invisible to Alembic, and autogenerate will cheerfully generate a
   migration that drops nothing and creates nothing.
3. `PYTHONPATH=. alembic -c infrastructure/alembic.ini revision --autogenerate -m "..."`.
4. Read the revision.
5. `uv run poe test-integration` and check `test_migrations.py` is green.

One table is mapped in exactly one context. When another context needs to read it, it gets a
read port, not a second ORM class: raw `text()` queries (`identity` and `network` both have an
`infrastructure/member_directory.py`) or the metadata-free `sqlalchemy.table()` handles in
`backend/paths/infrastructure/_member_tables.py`, which compose in Core queries but never
reach `Base.metadata`. A second mapping of the same table would make autogenerate emit
nonsense, which is the practical reason the rule is absolute.

## Repository conventions

Every database call goes through `run_db`:

```python
async def get_by_slug(self, slug: str) -> MemberProfile | None:
    async def go() -> MemberProfile | None:
        row = await self._s.scalar(select(MemberRow).where(MemberRow.slug == slug))
        return to_profile(row) if row else None

    return await run_db("members.get_by_slug", go)
```

`run_db` maps driver failures onto the application error hierarchy, so nothing above
`infrastructure/` ever catches a SQLAlchemy exception:

| Driver condition | Raised | HTTP |
| --- | --- | --- |
| `IntegrityError`, SQLSTATE `23505` | `ConflictError` | 409 |
| other `IntegrityError` (`23xxx`) | `ValidationError` | 422 |
| `OperationalError` | `RepositoryError` | 503 |
| any other `SQLAlchemyError` | `RepositoryError` | 503 |

The `op` string (`"members.get_by_slug"`) is the operation name that ends up in the error
message and the log line. Keep it `context.operation`.

Repositories never commit. The application service that owns the use case does, so a use case
touching several aggregates is one transaction. `get_db` yields one session per request.

## Inspecting the database

```bash
psql cdtm_community
```

```sql
\dt
\d members
\d accounts
\d jobs
select * from alembic_version;

-- who is bound to a login
select count(*) from accounts where member_id is not null;

-- rows the ingest matcher was unsure about (loader bookkeeping: these columns stay in the
-- database and reach the API only as the admin-only "review" block on a member profile)
select slug, name, match_method from members where needs_review order by name;

-- how many questions the Ask meter has counted this minute
select member_key, window_start, asked from ask_quota order by asked desc limit 10;
```

Through the API:

```bash
curl -s http://localhost:8000/health | python -m json.tool
```

### What the API is actually spending time on

`pg_stat_statements` groups every execution by query shape, which is the only way to see
that one endpoint's filter is a third of the database's time. Enable it from the Supabase
dashboard (Database → Extensions), not from a migration: the extension belongs to the
database instance rather than to this schema, `CREATE EXTENSION` needs a superuser Supabase
does not hand out, and a migration that tried would fail on every local clone.

```sql
-- slowest query shapes by total time
select calls, round(total_exec_time) as total_ms, round(mean_exec_time, 1) as mean_ms,
       left(query, 120) as query
from pg_stat_statements
order by total_exec_time desc
limit 20;

select pg_stat_statements_reset();   -- before a measurement run
```

## Troubleshooting

### Alembic cannot find a revision, or imports fail

Run from the repository root with `PYTHONPATH=.`:

```bash
PYTHONPATH=. python -c "from backend.core.app import create_app; create_app()"
```

`uv run poe migrate` sets `PYTHONPATH` for you; a bare `alembic` invocation does not.

### `prepared statement "__asyncpg_stmt_N__" already exists`

You are connected through the transaction pooler and `_is_transaction_pooled` did not say
so. It reads the port: 6543 is Supavisor in transaction mode, 5432 on the same host is
session mode, where prepared statements are safe and are kept. Use port 6543 in the URL, or
set `DATABASE_POOLER_TRANSACTION_MODE=true` if something in front of the pooler hides it.

### `type "gin_trgm_ops" does not exist`

`pg_trgm` was not created. Run `CREATE EXTENSION IF NOT EXISTS pg_trgm;` as a superuser on the
target database and re-run the migration.

### `function gen_random_uuid() does not exist`

Postgres older than 13. Upgrade, or `CREATE EXTENSION pgcrypto;`.

### `Refusing to wipe the database at ...`

The integration suite's loopback guard, refusing to `TRUNCATE` a non-local database. Unset
`DATABASE_URL` (an exported Supabase URL in the shell is the usual cause) and re-run.

### `Schema drift between migrations and ORM`

`test_migrations.py` found a difference between the migration chain and `Base.metadata`, and
printed it. Write the missing revision, or fix the one you wrote.
